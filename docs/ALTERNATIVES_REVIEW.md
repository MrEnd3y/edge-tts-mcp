# Сравнение существующих Edge TTS MCP-серверов

Дата: 2026-11-04. Это **статический обзор скачанного кода**, не результаты
запуска альтернатив. Чужие зависимости не устанавливались, серверы, тесты,
плееры, Telegram и OAuth не запускались. Файлы окружения и хранилища
авторизации не открывались. Это не полноценный аудит безопасности OAuth.

запрос: у зависимостей могут быть свои сетевые тайм-ауты. Но это не ограничение
общего времени операции и не замена корректной отмене дочерних процессов.

## 1. s-n-n/edge-tts-mcp

### Что хорошо

- Нормальная пакетная структура и CLI, сборка через Hatchling.
- Асинхронный `await Communicate.save()`;
  [tts.py:36–45](https://github.com/s-n-n/edge-tts-mcp/blob/2ee1d0040ea93521867055b27c2774d3e22e46e8/src/mcp_edge_tts/tts.py#L36-L45).
- Несколько системных аудиоплееров, конфигурация через Pydantic Settings.
- `speak` удаляет основной временный файл в `finally`.

### Почему не прямая замена для Hermes

- `speak` генерирует временный MP3, **ждёт локального воспроизведения**, возвращает
  текстовое подтверждение и удаляет файл. Постоянный путь для отправки клиенту
  не возвращается;
  [server.py:36–47](https://github.com/s-n-n/edge-tts-mcp/blob/2ee1d0040ea93521867055b27c2774d3e22e46e8/src/mcp_edge_tts/server.py#L36-L47).
- Список голосов ограничен первыми 20, без постраничного получения остальных;
  `server.py:67–75`.
- В синтезе и воспроизведении нет общего прикладного тайм-аута. В плеерах нет
  `finally` с остановкой процесса при отмене. Windows-плеер использует один
  фиксированный файл `edge_tts_play.ps1`: возможны гонки параллельных вызовов;
  `audio.py:127–151`.
- Зависимости `mcp>=1.0.0` и `edge-tts>=6.1.0` не ограничены сверху;
  [pyproject.toml:29–33](https://github.com/s-n-n/edge-tts-mcp/blob/2ee1d0040ea93521867055b27c2774d3e22e46e8/pyproject.toml#L29-L33).
  При этом код импортирует `mcp.server.fastmcp`: несовместимое обновление SDK
  остаётся риском. Установка не обязательно выберет старую библиотеку Edge TTS,
  но проверенная версия не закреплена.

**Вывод:** подходящий класс проекта для «озвучить на моём ПК», но для файлового
MCP в headless Hermes придётся менять основной сценарий.

## 2. saitrogen/edge-tts-mcp

### Что хорошо

- Асинхронное получение аудио через `Communicate.stream()` — это **не**
  проблемный `stream_sync()` старого eraincc.
- Есть фильтры голосов, настройка речи, Pydantic-модели, CLI, генерация JSON
  с временными метками слов.
- Удобен для Remotion/видеопроизводства, где важен заданный путь к MP3.

### Ограничения и риски

- Файл открывается сразу по пользовательскому `output_path` с режимом `wb`.
  Существующий файл может быть перезаписан; приватного staging/атомарной
  публикации нет;
  [server.py:33–72](https://github.com/saitrogen/edge-tts-mcp/blob/05903bbb5473bea628dd113c495adcf4ae4ac64a/src/edge_tts_mcp/server.py#L33-L72).
- При сетевой ошибке или отмене частичный MP3 не удаляется. Дедлайна всей
  операции нет. Возвращаемый `audio_size_bytes` не является проверкой формата
  или положительной длительности;
  `server.py:209–254`.
- OGG/Opus не реализован.
- Код собирает только `WordBoundary`, но не задаёт `boundary="WordBoundary"`
  в `Communicate`. В проверенной нами Edge TTS 7.3.1 по умолчанию используется
  `SentenceBoundary`: при такой зависимости возможны пустые метки слов и
  `duration_ms=0` даже при рабочем MP3. Это вывод по совместимости API,
  не воспроизведённый запуском этого проекта дефект.
- Документация обещает SSML, но собственной обработки SSML в пути синтеза нет.
  На это обещание нельзя полагаться без отдельного теста возможностей Edge TTS.
- `pyproject.toml` содержит `edge-tts>=6.1.12` и `mcp[cli]>=1.0.0` без верхних
  границ. `uv.lock` фиксирует Edge TTS 7.2.7 / MCP 1.26.0; обычная установка
  пакета через pip/uvx не обязана использовать этот lockfile.
- В metadata заявлена MIT, но отдельного файла LICENSE в скачанном дереве
  не найдено. Перед заимствованием/перераспространением стоит прояснить
  лицензионное уведомление и атрибуцию с автором.

**Вывод:** полезнее нашего для меток слов/видео, но не готовая замена под
требования «Hermes + Telegram + ограниченное время операции».

## 3. yanyan1115/yunxi-tts-mcp

### Что хорошо

- Самый близкий по функциям: MP3, OGG/Opus, опциональная отправка `sendVoice`.
- Голос параметризуется; китайский голос — значение по умолчанию, а не
  ограничение только китайским языком.
- Есть stdio, HTTP, выдача медиафайлов и OAuth-реализация.
- Контроль выхода за настроенную корневую папку; безопасное упрощение
  пользовательского имени файла; случайная часть имени по умолчанию.
- Зависимости закреплены: Edge TTS **7.2.8**, MCP **1.27.1**, httpx **0.28.1**.
  Это не доказательство, что 7.2.8 не работает; именно её мы здесь не тестировали.

### Важные проблемы для исходной задачи

- Синтез запускает отдельный CLI `edge-tts`, затем ждёт `process.communicate()`
  **без дедлайна**;
  [tts_mcp_server.py:516–582](https://github.com/yanyan1115/yunxi-tts-mcp/blob/26821f3363f90b9eb3f563a2f604c717714fe0cb/tts_mcp_server.py#L516-L582).
- При отмене ожидания нет `kill()`/`wait()` для CLI и FFmpeg. `finally`
  синтеза удаляет текстовый файл, но не гарантирует остановку процесса и
  удаление частичного аудио. Это недостаток кода отмены, не наблюдение
  реально оставшегося процесса.
- Перекодирование MP3 и конвертация OGG тоже без дедлайна и без остановки
  дочерних процессов при отмене; `tts_mcp_server.py:472–505,600–638`.
- **Конкретная несогласованность:** перекодирование MP3 использует настроенный
  `FFMPEG_COMMAND`, а конвертация OGG жёстко вызывает строку `"ffmpeg"`;
  [строка 621](https://github.com/yanyan1115/yunxi-tts-mcp/blob/26821f3363f90b9eb3f563a2f604c717714fe0cb/tts_mcp_server.py#L621).
  Указание собственного пути через `FFMPEG` не распространяется на OGG.
- Нет MCP-инструмента списка голосов: зарегистрированы только
  `text_to_speech` и `text_to_voice_note`; `tts_mcp_server.py:775–820`.
- При заданном `filename` результат не уникален: возможна перезапись/гонка.
  FFmpeg запускается с `-y`. Разбор готового контейнера/длительности отсутствует;
  проверяется код завершения и ненулевой размер.
- Единственный `smoke_test.py` печатает MCP-ответ, но не проверяет `isError`,
  наличие файла, корректность кодека или длительность. Он не заменяет
  автоматизированные регрессионные тесты.
- HTTP/OAuth/Telegram добавляют обязанности по защите и сопровождению,
  которые нашему локальному файловому MCP не нужны. Их наличие не означает,
  что удалённое развёртывание безопасно без отдельного аудита.

**Вывод:** лучший кандидат из этих трёх, если нужны именно HTTP и прямая
Telegram-отправка. Но ключевая проблема исходной задачи — зависание/надёжная
отмена — всё ещё требует доработки, плюс нужен список голосов.

## Решение без преувеличений

1. Идея Edge TTS через MCP **уже реализована многократно**. Наш сервер не
   новый движок и не уникальная концепция.
2. Среди этих трёх скачанных версий **не найдено готового совпадения со всем
   нашим набором требований**. Это не утверждение обо всех MCP-серверах в мире.
3. Если цель — только рабочий локальный сервер для Hermes, разумно оставить
   нашу небольшую реализацию: она уже проверена на нужных версиях Python и
   не требует добавлять OAuth, свой Telegram-клиент или воспроизведение.
4. Если приоритет — минимизировать собственную поддержку или получить HTTP/
   Telegram внутри MCP, можно доработать `yunxi` и предложить изменения автору.
   Это тоже потребует кода и тестов, а не только смены настройки.
5. Не стоит публиковать наш проект с обещаниями «первый», «единственный»,
   «самый надёжный». Корректное позиционирование: небольшой stdio MCP с
   MP3/OGG, дедлайнами, очисткой и проверками Python 3.12/3.14.

В версии 0.2.0 добавлены собственные SRT/VTT, метки слов, длинные тексты,
профили и `get_capabilities`. Это развитие после исходного сравнения, не
заимствование реализации из перечисленных проектов.

У нашего проекта тоже есть ограничения: нет HTTP/прямой
Telegram-отправки; сроки зависят от кооперативной отмены; успешные файлы
требуют политики хранения; Linux CI пока не запускался. Mutagen имеет GPL-
лицензию: лицензия нашего собственного кода MIT не отменяет обязательств
зависимости при распространении объединённого приложения.
